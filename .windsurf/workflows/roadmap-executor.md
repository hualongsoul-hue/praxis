# 按路线图逐步构建与验证

## 核心原则

- **严格遵循路线图**：以 `docs/ROADMAP.md` 为唯一执行依据，不得跳过、合并或自行添加阶段。
- **逐步执行、逐步验证**：每个任务完成后必须运行验证，每个阶段完成后必须与用户讨论。
- **禁止跳步**：只有当前阶段被用户确认为"理想状态"后，才能进入下一阶段。
- **禁止臆想**：不添加路线图中未定义的功能或逻辑，如发现遗漏应先与用户讨论。
- **保持可运行**：每个阶段结束时，项目必须处于可编译、可运行的状态。

---

## 执行流程

### 步骤 1 — 加载路线图

1. 读取 `docs/ROADMAP.md` 和 `docs/SRS.md`
2. 解析出所有阶段及其任务清单
3. 向用户展示当前要执行的阶段概览，确认开始

---

### 步骤 2 — 逐阶段执行（循环）

对路线图中的每个阶段，按以下子流程执行：

#### 2.1 阶段启动

- 展示当前阶段信息：
  - 阶段编号与名称
  - 目标描述
  - 任务清单（标注每个任务的验证标准）
- 使用 `todo_list` 工具创建当前阶段的任务清单，所有任务状态设为 `pending`
- 与用户确认：是否可以开始当前阶段？

#### 2.2 逐任务执行

对阶段内的每个任务：

1. **将该任务状态更新为 `in_progress`**
2. **编码实现**：
   - 严格按照 SRS 中的需求和验收标准编写代码
   - 遵循项目已有的代码风格和架构约定
   - 所有新文件必须包含必要的导入和依赖
   - 不添加路线图中未定义的额外功能
3. **即时验证**：
   - 编译/语法检查：确保代码无报错
   - 运行相关测试（如有）
   - 启动项目验证功能是否正常工作
   - 对照任务的"验证标准"逐条检查
4. **如果验证失败**：
   - 分析根因，修复问题
   - 重新验证，直到通过
5. **将该任务状态更新为 `completed`**

#### 2.3 阶段验证

当阶段内所有任务完成后：

1. **完整启动项目**，确保项目可正常运行
2. **逐条对照**阶段的目标描述和验证标准
3. **向用户展示阶段成果**：
   - 本阶段完成了哪些内容
   - 新增/修改了哪些文件
   - 项目当前运行状态截图或日志
   - 是否存在已知问题或技术债务

#### 2.4 用户讨论与确认（关键门禁）

向用户提出以下讨论要点：

1. **功能是否符合预期？** — 与 SRS 中的验收标准对照
2. **交互/界面是否满意？** — 如涉及 UI
3. **是否有需要调整的地方？** — 收集反馈
4. **是否可以进入下一阶段？** — 明确获得用户确认

**处理反馈的规则**：

- 如果用户提出修改意见：
  1. 记录修改需求
  2. 评估修改是否影响后续阶段
  3. 实施修改
  4. 重新验证
  5. 再次进入讨论确认环节
- 如果修改涉及路线图调整：
  1. 先更新 `docs/ROADMAP.md`
  2. 与用户确认更新后的路线图
  3. 再继续执行
- **只有用户明确表示当前阶段达到理想状态后，才标记阶段完成并进入下一阶段**

---

### 步骤 3 — 项目收尾

当路线图所有阶段全部完成后：

1. **全量验证**：完整运行项目，检查所有功能
2. **生成项目总结**，保存为 `docs/PROJECT_SUMMARY.md`，包含：
   - 项目最终架构概览
   - 已实现的功能清单（对照 SRS）
   - 技术栈与依赖说明
   - 启动与部署说明
   - 已知问题与后续建议
3. **与用户做最终确认**：项目是否达到整体理想状态

---

## 异常处理规则

| 场景 | 处理方式 |
|------|----------|
| 执行中发现 SRS 遗漏 | 暂停执行，与用户讨论，更新 SRS 后继续 |
| 技术方案需要调整 | 暂停执行，说明原因，与用户讨论替代方案 |
| 依赖库不兼容或不可用 | 查找替代方案，与用户讨论后决定 |
| 阶段反复未通过确认 | 回顾 SRS 相关章节，重新对齐需求理解 |
| 用户要求跳过某阶段 | 评估影响，明确告知风险，由用户最终决定 |

---

## 输出物清单

每个阶段结束后，项目中应包含：

- 该阶段路线图中定义的所有输出物（代码、配置、文档等）
- 更新后的 `todo_list`（反映完成状态）

项目整体结束后，额外输出：

- `docs/PROJECT_SUMMARY.md` — 项目总结文档
